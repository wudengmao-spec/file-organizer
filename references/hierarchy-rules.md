# 层级设计规则

分类轴和层级是**判断题**，脚本只能校验数不能校验对错。这份文件给判断标准。

## 1. 结构的来源是证据

顶层目录的 `title`（从 README/AGENTS 首行提取）是最强证据。排序强度：

1. 目录自带的 README/AGENTS/package.json 标题 —— 最强，说明这个目录自认是什么
2. 目录里样例文件名的语义聚集 —— 中等，需要你读内容确认
3. 扩展名分布 —— 最弱，只能作为旁证

**只有第 3 类证据时**（比如全是 `IMG_2341.png`），说明这个目录的内容没有可读的
语义线索。此时正确做法是把它整体归到"待定"或按来源归类（`截图/`、`下载/`），
而不是靠文件名猜测它属于哪个项目。

## 2. ≤3 层，且每层都要有区分度

约束是"深度 ≤3"，但更有用的是这个判据：**每一层都应该让下一步选择更容易。**

- 加一层之后，用户在这个桶里能做出一个明确的选择吗？不能 → 这层不该加
- 桶里只有 1-2 个子项，且它们和父桶名字没有本质区别 → 这层是冗余的，合并上去
- 第 3 层通常只用来区分"同一主题下的不同载体"（`03-素材/截图/项目A/` vs
  `03-素材/截图/项目B/`）

反例（冗余嵌套）：

```
资料/               ← "资料" 和 "文档" 是一回事
├── 文档/
│   ├── 项目/       ← "项目文档" 和 "项目" 是一回事
│   └── 资料/       ← 同上
```

正例：

```
01-创作/长篇/        ← "创作"分长短篇，"长篇"下是具体作品
02-研究/课题/
```

## 3. 按"你会怎么找"分，不按"它是什么格式"分

这是最常见的错误。判断方法：**用户下次找这张图时，他脑子里冒出的是哪个词？**

- 冒出"项目A的封面" → 归 `项目A/`，不是归 `图片/`
- 冒出"2024年报" → 归 `财务/2024年报.pdf`，不是归 `PDF/`

**格式只能是最内层的区分手段，且必须让位于项目归属。** 一个项目的封面图、
截图、录屏、说明文档，都属于该项目 —— 它们是项目的附属物，不是素材。

## 4. 项目原子性

一个目录如果自成一个单元（有 README/AGENTS/package.json/自己的一套结构），
就**整体归位**，别拆。

判定信号（命中任一即视为项目根）：

- 顶层有 `README.md` / `AGENTS.md` / `CLAUDE.md`
- 有 `package.json` / `pyproject.toml` / `go.mod` / `Cargo.toml`
- 内部目录结构明显不是平铺文件，而是有自己的一层含义
- `inventory.json` 里 `title` 非空

被判定为项目根的目录，它的**全部内容**跟着走。哪怕里面有 3 张 png 和 2 个 pdf，
也不要为了"归类整齐"把 png 抽出来。

**反例（真实发生过的错误）**：

```
❌ 01-项目/项目Alpha/图像/封面.png     ← 把封面图抽到"图像"桶
   01-项目/项目Alpha/文档/说明.md     ← 把说明抽到"文档"桶
✅ 01-项目/项目Alpha/封面.png         ← 项目整体搬，内容原样跟随
   01-项目/项目Alpha/说明.md
```

看起来"更整齐"，实际后果：项目目录被掏空成两个跨桶的碎片，用户想看"项目Alpha
有什么"时要去两个地方拼。而且这正是"按格式分"这个错误分法伪装成"分类"的形态
—— 桶名叫"图像""文档"，分类依据是扩展名，不是归属。

判断标准：**桶名如果描述的是"文件长什么样"而不是"文件属于谁"，就是错分。**
`图像/`、`文档/`、`压缩包/`、`PDF/` 这些都是格式桶；`项目Alpha/`、`财务/`、
`2024年报/` 这些是归属桶。

## 5. 重复类别检查

提交结构前，逐条检查有没有同义桶：

- `Projects/` 和 `Work/Projects/` —— 同一意图拆在两个地方，用户要记两处
- `文档/` 和 `资料/` —— 中文近义词，多数场景是同一个意思
- `图片/` 和 `素材/` —— 同上

**同义桶必须合并。** 合并时保留更具体、更常用的那个词。

同时检查**跨层重复**：如果第 2 层和第 3 层出现同名桶（如 `项目/项目/`），
说明层级划分错了。

## 6. 跨域 tie-break

一个文件同时像两个类别（一份"2024 财务分析"既是资料又是项目产出）时：

1. **有明确产出方 → 归产出方。** 财务部做的分析，归 `02-文档/财务/`，不归 `参考资料/`
2. **有截止日期/会持续更新 → 归项目类。** 活的项目产出在推进中，参考资料是沉淀的
3. **两者都不明确 → 归更具体的那一边**（`财务` 比 `参考资料` 具体）

参考 Orderly 的归属门原则：**只归你能确定归属的**。判断不了就留在原地，
列进待定清单 —— 错误的归类比不归类代价更高，因为它会静默地搬走文件。

## 7. 命名

- **第 1 层用数字前缀排序**（`01-工具`、`02-文档`）—— 用户靠前缀建立心智顺序
- **桶名用名词，不用动宾结构**（`文档` 而非 `整理好的文档`）
- **中文优先**，除非目标目录里已经是英文/代码项目
- **桶名要短** —— 第 1 层桶名会出现在每一层的路径里，路径长度是硬约束（250 字符）
- **不要在桶名里带序号以外的排序语义**（`02-财务` 和 `02-重要财务` 混用会乱）

## 8. 常见结构模式（按证据选，不是套模板）

观察到对应的目录特征时才用：

| 证据 | 可考虑的结构 |
|---|---|
| 顶层有大量互不相关的项目目录 | 按项目分：`01-项目/<领域>/<项目名>` |
| 顶层是杂乱的单文件 + 少量文件夹 | 按类型分：`01-文档`、`02-媒体`、`03-压缩包` |
| 顶层有明确的"工作/个人"分区 | 沿用它：`01-工作/...`、`02-个人/...` |
| 已有 PARA 结构（Inbox/Projects/Areas/Resources） | 沿用 PARA，不要另起编号桶 |
| 顶层是按年份分的 | 沿用年份，但第 1 层会很快超 7 个桶，注意上限 |
