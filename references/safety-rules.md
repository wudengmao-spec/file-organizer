# 安全边界详解

工具的职责：把"不能靠判断解决"的部分机械地挡住。这份文件说明挡了什么、为什么。

## 1. 禁删

**整理流程中不存在任何删除路径。** 脚本的 `apply` 子命令只做移动和重命名。

清理走独立的三级阶梯（`clean` 子命令），每一级都可恢复：

| 级 | 动作 | 可恢复性 |
|---|---|---|
| 1（默认） | 移入 `<root>/_trash-candidates/<时间戳>/`，同目录留 `_origins.md` 记录来源 | 手动移回即可 |
| 2（`--recycle`） | 送系统回收站 | 从回收站还原 |
| 3 | **不存在** | 硬删除路径没有实现，也不该加 |

`clean` 不加 `--apply` 时是纯只读清单。`--apply` 进暂存区；`--recycle` 送回收站。
`--recycle` 在没有回收站机制的系统上会把该项留在原地并报告，不做替代性硬删。

## 2. 敏感路径保护

以下路径在**盘点阶段就被排除**，不读取内容、不修改、不移动、不删除：

| 类别 | 具体 |
|---|---|
| 密钥与证书 | `*.pem` `*.key` `*.pfx` `*.p12` `*.asc` `*.gpg` `*.kdbx` `*.jks` `*.keystore` `*.ppk` |
| 私钥与凭据 | `id_rsa` `id_ed25519` `id_ecdsa` `id_dsa` `credentials` `secrets.json/yaml/yml` `shadow` |
| 认证配置 | `.netrc` `_netrc` `.npmrc` `.pypirc` `known_hosts` `authorized_keys` `master.key` |
| 环境变量文件 | `.env` `.env.local` `.env.production` 等所有 `.env*` |
| 密钥目录 | `.ssh/` `.aws/` `.gnupg/` `.azure/` `.kube/` `.docker/` `.config/gcloud/` `keychains/` `passwords/` |
| 浏览器与系统 | `User Data` `Profiles` `Profile Default` `Login Data` |

**为什么排除而不是"顺手整理"**：密钥文件被搬到新目录后，旧位置的权限保护就失效了；
证书被误改名会让依赖它的程序直接失效。用户说"整理文件"时，指的是工作资料，
不是指把这些东西也归类。

被排除的路径会记进 `inventory.json` 的 `protected_paths`，并在对用户的报告里
说明数量 —— 是"被保护"，不是"被丢弃"。

## 3. 符号链接

不跟随。符号链接指向根外的目标时，跟随它等于把根外的东西拖进来。

处理方式：当作不透明对象记录在 `symlinks` 里，报告给用户，不自动动它。
如果用户明确要处理某个链接，单独讨论。

## 4. 原子包

`.app` `.photoslibrary` `.pages` `.numbers` `.key` `.framework` `.bundle`
这类目录，内部结构由应用程序定义，拆开会导致应用无法打开。

处理方式：整体移动，永不逐文件分类。盘点时记进 `atomic_bundles`。

## 5. 同内容去重

两级识别，避免对大文件做无意义的哈希计算：

1. 按 `size` 分组 —— 大小不同的必然不是重复
2. size 相同的组内才算 `sha256`

大小超过 `--hash-limit`（默认 64MB）的文件只比大小，不算哈希。

**去重的结果只是候选，保留哪份是判断题。** `size` 和 `sha256` 都相同的两份
文件，仍可能有一份是"我改过但忘了保存"的那份。所以工具只报出重复组，
是否合并由用户决定。

**哈希相同 ≠ 可以合并。** 同一份内容的不同副本，在语义上可能是不同的时间片
或不同版本 —— 例如 `2023年报.pdf` 与 `2024年报.pdf` 如果字节完全相同（占位内容
常见），哈希判定它们是"重复"，但它们代表两个年度，去重等于直接丢失一年数据。
文件名承载的时间/版本语义与哈希冲突时，**以文件名为准，保留两份**。

去重只有在用户明确说"这两份是同一份，删一份"时才能执行。

## 6. 冲突策略

目标已存在同名文件时：

- **不覆盖。** 自动改名为 `name_1`、`name_2`，并在回滚表 `collisions` 里记录
  原目标名和实际改名
- 脚本**不做**哈希比对来决定是否跳过 —— 那会误判（两份内容相同但用户想要两份，
  例如带不同批注的副本）。改名让两份都在，是最安全的选择

## 7. 自噬与越界

- 目标不能是源自身或源的子目录（会把目录移进自己）
- 目标路径不能含 `..`（越出目标根）
- 目标落在源目录内部会给警告

## 8. 路径长度

本机 `LongPathsEnabled=0`，Windows `MAX_PATH` 是 260 字符，超了直接失败。
脚本上限设 250（留 10 字符余量），接近上限（>230）给警告。

路径长度是 3 层约束之外的**第 4 个硬约束** —— 第 1 层桶名出现在每一层路径里，
桶名越长越容易触顶。设计结构时桶名要短。

## 9. 对账与回滚契约

**对账**（`apply --apply` 自动执行，`verify` 可单独重跑）：

- 文件数守恒：移动前统计 vs 落盘后统计
- 字节数守恒：同上，比文件数更严，能抓到截断和部分移动
- 源端残留报告：未被映射覆盖的残留会列出，并明确标注"**未被删除**"
- 抽样哈希：单文件移动记录移动前 sha256，verify 时抽样比对

**回滚表** `map.rollback.json`：

```json
{
  "generated_at": "...",
  "root": "...",
  "entries": [{ "to": "...", "from": "...", "files": 12, "bytes": 34567, "sha256": "..." }],
  "collisions": [{ "target": "...", "renamed_to": "..." }]
}
```

回滚是**整批逆序**执行：倒序遍历 `entries`，只有当目标存在且原位置空着时才移回。
原位置非空说明用户动过，跳过并报告，不强行覆盖。

## 10. 跨盘移动

源和目标在不同盘符/文件系统时，先复制到目标、校验 size+sha256 确认无误，
再删除源。校验不过就保留源并报告 —— 不做"复制完就删源"的赌注。

## 11. 硬边界汇总

| 约束 | 值 | 谁执行 |
|---|---|---|
| 层级深度 | ≤ 3 | 脚本校验 |
| 第 1 层桶数 | ≤ 7 | 脚本校验 |
| 第 2/3 层子项数 | ≤ 3 | 脚本校验 |
| 目标路径长度 | ≤ 250 字符 | 脚本校验 |
| 删除 | 禁止（清理只走暂存/回收站） | 脚本强制 |
| 同名覆盖 | 禁止（自动改名并记录） | 脚本强制 |
| 敏感路径 | 排除 | 脚本强制 |
| 符号链接 | 不跟随 | 脚本强制 |
| 原子包 | 整体处理 | 脚本强制 |
| 分类轴是否合理 | —— | **你判断** |
| 重复保留哪份 | —— | **你判断** |
| 什么算垃圾 | —— | **你判断** |
